# حالة بيئة Staging

**آخر تحديث: 4 نوفمبر 2026**

## الإنتاج الحالي

- التطبيق يعمل على AWS EC2، وقاعدة البيانات PostgreSQL على RDS، والملفات في S3 خاص باستخدام IAM Role.
- عنوان API الإنتاج: `https://13.49.114.20/api/v1`.
- المستخدم تحقق من `GET /api/v1/health/ready` عبر HTTPS وكانت قاعدة البيانات `CONNECTED`.
- GitHub Actions مضبوط لتشغيل الفحوص ثم نشر تغييرات `main` عبر SSM. راجع نتيجة الـworkflow وSHA المنشور بعد كل إصدار.
- التعديلات الجديدة تُرفع إلى `dev` فقط حتى يطلب المستخدم إصدارًا على `main`؛ push إلى `dev` يشغّل CI ولا ينشر على EC2.
- تفاصيل إعداد EC2 وRDS وS3 والنشر موجودة في [دليل AWS](AWS_DEPLOYMENT_AR.md)، وخطوات GitHub Actions في [دليل GitHub](GITHUB_AUTOMATION_AR.md).

## Staging منفصل

لا توجد بيئة Staging منفصلة حتى الآن. قيمة `staging` في Bruno تظل placeholder وتنتهي بـ`.invalid`؛ لا تستخدمها للاختبار. استخدم `local` للتطوير أو `production` لاختبار الإنتاج بحذر، ولا تشغّل مجموعة `bruno/smoke` على الإنتاج لأنها تغيّر البيانات.

لو أُنشئت بيئة Staging لاحقًا، سجّل عنوانها الحقيقي وحالة قاعدة البيانات والخدمات الخارجية ونتائج الاختبار في هذا الملف. يجب أن تستخدم قاعدة بيانات وأسرارًا منفصلة عن الإنتاج.

## حدود التحقق الحالي

- نجاح فحص الجاهزية يثبت اتصال API بقاعدة RDS وتطبيق migrations، لكنه لا يختبر تسليم البريد أو Google OAuth أو رفع S3.
- تم تكوين Gmail SMTP وقبول رسالة OTP حقيقية في اختبار سابق؛ لا يثبت ذلك تسليم كل رسالة مستقبلية.
- Google OAuth يحتاج تنفيذ تسجيل الدخول داخل تطبيق Android وإرسال ID token وchallenge/nonce صالحين. Apple مؤجل.
- خدمة إعادة الكتابة بالذكاء الاصطناعي غير مفعّلة بمزوّد إنتاج معتمد.
- تفاصيل حالة كل ميزة واختبارها في [حالة التسليم](DELIVERY_STATUS.md) و[جدول APIs](APIS_ACTUAL_AR.md).
